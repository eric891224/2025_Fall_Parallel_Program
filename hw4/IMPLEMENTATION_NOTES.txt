================================================================================
OPTIMIZATION APPROACH
================================================================================

STRATEGY: Parallelize the nonce search loop across multiple CPU threads

RATIONALE:
  - Mining is "embarrassingly parallel" (each nonce computation is independent)
  - No data dependencies between iterations
  - Perfect scaling across CPU cores
  - Minimal synchronization overhead

IMPLEMENTATION:
  1. Divide 32-bit nonce space into NUM_THREADS equal ranges
  2. Launch one thread per range
  3. Each thread sequentially searches its range
  4. Use std::atomic<bool> for lock-free early termination
  5. First thread to find solution signals others to exit

SYNCHRONIZATION:
  - std::atomic<bool> found    (all threads read, one writes)
  - No mutexes, no locks, no semaphores
  - Each thread has private hash buffer (no contention)

================================================================================
TECHNICAL DETAILS
================================================================================

NONCE DISTRIBUTION:
  Total nonce space: 0x00000000 to 0xffffffff (4,294,967,296 values)
  Per thread: 4,294,967,296 / 64 = 67,108,864 nonces
  
  Thread 0: 0x00000000 to 0x03ffffff
  Thread 1: 0x04000000 to 0x07ffffff
  ...
  Thread 63: 0xfc000000 to 0xffffffff

CRITICAL BUG FIXED:
  Initial attempt: nonce_range = (0xffffffffU + 1) / num_threads
  Problem: (0xffffffffU + 1) = 0 in 32-bit arithmetic (overflow!)
  Solution: Use 64-bit: nonce_range = (1ULL << 32) / num_threads

THREAD SAFETY:
  - Atomic bool prevents race conditions
  - Atomic is lock-free (uses CPU hardware)
  - All reads are wait-free (no blocking)
  - Single write (first finder) is safe

EARLY TERMINATION:
  - All threads periodically check: if(result.found) return;
  - No need to wait for slow threads
  - Significant speedup when solution found early

================================================================================
DESIGN DECISIONS & RATIONALE
================================================================================

1. CPU Threading vs GPU
   ✓ Why CPU: Fast to implement, works on any machine
   ✗ Why not GPU: Device SHA256 adds complexity, CPU sufficient

2. Atomic Operations vs Mutexes
   ✓ Why atomic: Lock-free, faster, simpler, cache-friendly
   ✗ Why not mutex: Potential contention, requires lock management

3. Per-thread vs Shared Memory
   ✓ Why per-thread: No synchronization, cache-friendly
   ✗ Why not shared: Would require locks for coordinated update

4. Early Termination
   ✓ Why implement: Reduces wasted computation
   ✗ Why not: Simpler code, but much slower if solution found early
